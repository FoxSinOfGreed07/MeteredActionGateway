# Decisions

Each entry gives the **chosen** option, the **rejected** option (the strongest rival, not a strawman), and the
**specific failure** the choice prevents, plus a line on the other options and the trade-off accepted. The longer
rationale, with the pushback I expect and my answer to it, is in [`decisions/recommended.md`](decisions/recommended.md).

## Assumptions the decisions rest on

| # | Assumption |
|---|---|
| S1 | An **ERP lane** is one ERP endpoint with its own rate limit. Tenants map to a lane plus a company code, and several tenants can share a lane. |
| S2 | The ERP has **no idempotency keys**. It stores a free-text `reference` on each payment and supports lookup by it, but does not enforce that references are unique. |
| S3 | ERP reads can **lag** behind its writes. The normal maximum lag is declared per lane (`max_read_lag_ms`, 5 s). A 10-minute stale window violates this, so it must be *detected*, not assumed away. |
| S4 | A lagging read view is a consistent snapshot as of some past moment (replicas apply commits in order). |
| S5 | `pay_invoice` pays the **full open amount**. The agent states the amount; a mismatch is a permanent validation error. |
| S6 | ERP `503` means "not processed". `500`/`502`/`504` mean "may have been processed". |
| S7 | Any number of `api` and `worker` processes may run; all coordination goes through Postgres or Redis. |
| S8 | Credits are integers. Money is integer paise, INR. |

**Principle:** *Redis holds nothing whose loss could lose an action or money.* Redis holds cache entries,
rate-limit tokens, cooldowns and coalescing leases. Lose them and the system gets slower, never wrong. That's why
compose runs Redis with persistence turned off.

## D1: How the ERP write happens once

- **Chosen: our own dedupe table.**
  - `UNIQUE (tenant_id, idempotency_key)`. Keys are generated by the client, scoped to the tenant (taken from the API credential), and kept forever.
  - A hash of the request body is stored next to the key, so the same key with a different body returns `422`.
  - A compare-and-set `QUEUED → DISPATCHING` with a lease is committed *before* the HTTP call, so exactly one worker sends.
  - Our action id is stamped on the ERP document as its reference.
- **Rejected: an idempotency key at the ERP.**
- **Failure prevented:** a double payment when the ERP has no dedupe (Tally, most SAP posting paths) or its dedupe window has expired.
- **Others:**
  - *Optimistic lock* guards concurrent *different* writes, not a repeat of the same one.
  - *Check-then-write* without ownership is a time-of-check/time-of-use race. We only check while holding the action's lease.
- **Trade-off:** we own the exactly-once logic (state machine plus reconciler), and every ambiguous outcome costs one extra lookup.
- **Code:** `src/gateway/actions/submit.ts`, `src/gateway/dispatch/claim.ts`, `src/gateway/actions/state-machine.ts`.

## D2: What happens when the outcome is unknown after a timeout

- **Chosen: mark UNKNOWN and reconcile asynchronously.** Timeouts, resets, `5xx` other than `503`, and expired leases all move the action to `UNKNOWN`, and the hold is kept. The reconciler then looks the payment up by reference.
  - **"Found"** is trusted at once.
  - **"Not found"** is trusted only when all four of these hold:
    1. `now ≥ unknown_since + request_timeout + max_read_lag`
    2. there is no stale-read evidence on the lane in Postgres
    3. a later payment of ours that we know committed (a *witness*) is visible in the same read view
    4. two consecutive "not found" results have been seen
  - Only then is the action re-sent with the **same** reference. After 3 ambiguous cycles it is failed and released instead.
- **Rejected: query the ERP first** (inline, acting on the immediate answer).
- **Failure prevented:** a double payment, or a wrongful refund, caused by trusting a "not found" too early. That can happen before an abandoned request commits, or from a lagging replica.
- **Others:**
  - *Retry* double-pays whenever the first attempt committed.
  - *Refund* gives a free action whenever it did commit.
- **Trade-off:** credits stay held while an action is UNKNOWN, and a "not found" takes at least ~10 s to resolve (longer while the ERP is degraded).
- **Code:** `src/gateway/dispatch/settle.ts` (`markUnknown`), `src/gateway/dispatch/recovery.ts`, `src/gateway/reconcile/`.

## D3: Where the debit sits relative to the action

- **Chosen: two-phase hold and capture.**
  - A `HOLD` is written in the admission transaction.
  - Success writes `CAPTURE` (≤ hold) plus a `RELEASE` of any remainder.
  - Confirmed non-execution writes `RELEASE`, with a reason.
  - `UNKNOWN` keeps the hold.
- **Rejected: debit first, then act** (refund on failure).
- **Failure prevented:**
  - An unresolved action looking identical to a finished one. With debit-first, a crash between the failure and the refund leaves an overcharge nothing can detect.
  - With holds, the ledger proves that every action settled exactly once.
- **Others:**
  - *Act-then-debit* executes before checking funds, so the wallet goes negative (Scenario 4).
  - In a *saga*, the "compensation" for a posted SAP payment is a reversal document, which is a real accounting event.
- **Trade-off:** three entry kinds; tenants see `available` and `held` separately.
- **Code:** `src/gateway/wallet/ledger.ts`, `src/gateway/dispatch/settle.ts`.

## D4: Cache pattern for ERP reads

- **Chosen: read-through.** `CachedReader` is the only path to ERP vendor and invoice reads. It enforces the budget, the sequence guard and coalescing in one place.
- **Rejected: cache-aside.**
- **Failure prevented:** "set after invalidate": a slow reader writing an old value back after a webhook deleted it. Every fill goes through one atomic, sequence-guarded Lua script.
- **Others:**
  - *Write-through* never sees changes made in SAP through other channels (Scenario 6).
  - *No cache + coalescer* spends an ERP rate-limit token on every read, and payments need those tokens.
- **Trade-off:** less flexibility at call sites.
- **Code:** `src/gateway/cache/cached-reader.ts`, `src/redis/lua/cache_*.lua`.

## D5: How cached data is invalidated

- **Chosen: webhooks with per-object sequence numbers.**
  - A per-object high-water mark (HWM) is learned from webhooks and from our own payment responses.
  - Values below the HWM are never served or stored. TTL = budget − max read lag is the backstop for lost webhooks.
- **Rejected: TTL only.**
- **Failure prevented:**
  - serving data we've already been told is wrong
  - cache rollback by duplicate or out-of-order webhooks
  - caching a stale ERP read (each such rejection is also reported as stale-read evidence for D2)
- **Others:**
  - *Delete-on-write* misses changes made through other channels.
  - *Versioned keys* need a version lookup on every read, and they don't stop stale fills.
- **Trade-off:** depends on the ERP emitting sequence numbers. Any object type that can't fall back to TTL only, with a short budget.
- **Code:** `src/gateway/cache/webhook-ingest.ts`, `src/gateway/cache/hooks.ts`, `src/redis/lua/cache_*.lua`.

| Object | Budget | TTL | Invalidated by |
|---|---|---|---|
| Vendor master | 60 s | 55 s | webhook seq; TTL |
| Invoice | 15 s | 10 s | own payment response seq; webhook seq; TTL |
| Payment lookup by reference | never cached | — | — |
| Classification result | unbounded | — | immutable; key includes model + prompt version |

## D6: Stampede protection on a hot vendor

- **Chosen: request coalescing.** An in-process single-flight, plus a Redis lease so only one *process* loads. Everyone else waits for the fill.
- **Rejected: stale-while-revalidate.**
- **Failure prevented:** 1,000 simultaneous misses becoming 1,000 ERP reads, burning the lane's rate budget and triggering 429s that stall payments. Measured: 1,000 concurrent requests → **1** ERP read, also across two API instances.
- **Others:**
  - A *bare per-key lock* gives waiters no result.
  - *Probabilistic early refresh* doesn't guarantee a single read.
  - *SWR* serves values past their TTL; it's an add-on to coalescing, not a replacement.
- **Trade-off:** waiters wait for one ERP read. If that read fails, they get `503` rather than a value past its budget.
- **Code:** `src/gateway/cache/singleflight.ts`, `src/gateway/cache/coalesce-lease.ts`.

## D7: Concurrency control on a tenant's wallet

- **Chosen: an atomic conditional update on a wallet projection.**
  - One statement: `UPDATE wallets SET available = available − c, held = held + c WHERE available >= c` and the `HOLD` insert, in a single CTE.
  - `CHECK (available >= 0)` backs it up.
  - The ledger is the truth: the projection is kept in the same transaction and verified against `SUM(ledger)`.
- **Rejected: `SELECT … FOR UPDATE`.**
- **Failure prevented:** Scenario 4's race (500 credits, two 300-credit holds → −100). The check and the write are one statement, so no code path can forget the lock.
- **Others:**
  - A *Redis lock* can expire while its holder is still writing, and it sits outside the Postgres transaction.
  - A *single-writer queue* makes admission asynchronous, but rejection has to happen at hold time.
- **Trade-off (measured):** a tenant's admissions serialize on its wallet row through the commit: ~330 submits/s for a single tenant, ~1,250/s across 5 tenants.
- **Code:** `src/gateway/wallet/ledger.ts` (`placeHold`).

## D8: Queue for action execution

- **Chosen: a Postgres-backed queue.**
  - The `actions` table *is* the queue. Enqueuing is the insert in the admission transaction.
  - Claims use `FOR UPDATE SKIP LOCKED` plus a lease, with the least-recently-served tenant first.
- **Rejected: BullMQ.**
- **Failure prevented:**
  - The dual-write gap: with BullMQ, a crash between the Postgres commit and `queue.add` leaves credits held for an action nothing runs.
  - First-in-first-out unfairness: open-source BullMQ has no round-robin across groups, so a tenant's 100 actions wait behind another tenant's 4,900.
- **Ordering, retry, replay:**
  - **Ordering** isn't needed (same-invoice conflicts are ruled out by the conflict index).
  - **Retry** uses `next_attempt_at` plus the lane cooldown, with no cap for outcomes that were definitely not committed.
  - **Replay:** `actions` + `action_events` are the history.
- **Others:**
  - *Kafka*: a 429 blocks the whole partition, there's no per-message delay, and replaying payment commands is dangerous.
  - *SQS*: doesn't run locally, and there's no replay.
- **Trade-off:** about 200 lines of claim/lease/backoff code we own, and polling.
- **Code:** `src/gateway/dispatch/`.

## Other decisions

| # | Chosen | Rejected | Failure prevented |
|---|---|---|---|
| A1 | Node + TypeScript + Hono; Postgres 17; Redis 7 | NestJS / Express | framework ceremony eating a 48 h budget; Hono's `app.request` makes in-process tests trivial |
| A2 | Kysely + plain SQL migrations (snake_case 1:1) | Prisma | the correctness-critical SQL (conditional update, SKIP LOCKED, partial index, triggers) hidden behind an ORM or in untyped raw escapes |
| A3 | Separate `api`, `worker`, `mock-erp` processes | one process | a dispatch backlog or crash taking down submit; the crash demo needs to kill the worker alone |
| A4 | Limits, cooldown and health per **lane**; tenants share lanes | one global limiter | one ERP's 429 storm stopping traffic to every other ERP |
| A5 | Round-robin by least-recently-dispatched tenant | FIFO | tenant B's 100 actions waiting behind A's 4,900 (measured with A=4,000 queued first, B=C=500: B and C finished at completions #1,500 and #1,499 of 5,000; FIFO would put them after #4,000) |
| A6 | Redis token bucket per lane; on 429, one cooldown per window plus a single probe | in-process limiter per worker | N workers sending N× the quota; everyone hammering the ERP during a 429 window (measured: 24 × 429 across a 15 s outage with 5,000 queued actions) |
| A7 | Per-tenant pending cap → 429, not stored | unbounded queue | a runaway agent filling the DB and locking all its credits |
| A8 | Conservative taxonomy: only provably pre-commit failures are retryable; anything unknown → UNKNOWN | timeouts/5xx retryable | a double payment from retrying a committed request |
| A9 | 402/409 stored as REJECTED and replayed; 400/422/429 not stored | never store rejections | the same key producing two different outcomes |
| A10 | Conflict key per action type; partial unique index over QUEUED/DISPATCHING/**UNKNOWN**; the ERP's "already paid" check as backstop | ERP check alone | two payments in flight for one invoice, including while the first is "maybe paid" |
| A11 | Only actions are metered (pay 300; classify 20, or 2 on a cache hit) | metering reads | ledger write amplification; charging for gateway-internal refreshes |
| A12 | Holds never expire while an action may have executed; never-sent QUEUED actions expire after 24 h | a TTL on every hold | a free action when an UNKNOWN payment did commit |
| A13 | LLM cache key = sha256(tenant, task, schema, normalized input, model, prompt version); immutable rows | key on content only | a prompt/model upgrade never taking effect, or answers changing with no record why; cross-tenant leakage |
| A14 | Deterministic fake classifier by default; Claude adapter (`claude-opus-5`, effort low, structured output, server-side fallbacks) when a key is set | requiring a real LLM | non-deterministic, paid, network-dependent tests |
| A15 | Durations scaled by `SCENARIO_TIME_SCALE`; realtime mode runs the doc's numbers | fake timers | Node's fake clock disagreeing with Postgres `now()`, Redis `TIME` and the mock ERP |
| A16 | `transition()` CAS + an `action_events` row in the same transaction; DB trigger enforces legal transitions and immutable columns | a free `state` column | an illegal transition (e.g. FAILED → SUCCEEDED after a release) slipping through |
| A17 | HMAC-SHA256 on webhooks | unauthenticated webhooks | a forged huge `seq` turning every read into a 503 |
